# Локальный сервис кросс-сервисного анализа логов и поиска первопричин (RCA Logs Analyzer)

## 1. Назначение сервиса

**RCA Logs Analyzer** — это локальная, полностью изолированная от внешней сети система для глубокого анализа логов микросервисной архитектуры (5–15 сервисов), поиска межсервисных корреляций и автоматического определения **первопричины инцидента (Root Cause)**, **путей распространения сбоя (Propagation)**, **вторичных симптомов (Symptoms)** и **фонового шума (Noise)**.

Каждое утверждение системы подтверждается **проверяемыми артефактами (`E-01`, `E-02`, …)** — точными сырыми строками с контрольными суммами `SHA-256`, ссылками на исходный файл и номер записи, цепочками прохождения запросов между сервисами, статистическими расчётами и векторными SVG-графиками.

Для глубокой интерпретации результатов система формирует очищенный от секретов и персональных данных **пакет для Gemini (`gemini_bundle.md`)**, готовый к отправке во внешнюю LLM вручную.

## 2. Ключевые условия эксплуатации и ограничения

| Параметр | Значение и реализация |
|---|---|
| **Режим работы** | 100% локальный и изолированный (`air-gapped`). Контейнеры работают во внутренней сети Docker (`internal: true`), порты привязаны только к `127.0.0.1`. Сервис **не делает никаких исходящих сетевых запросов** (ни в Loki, ни в интернет). |
| **Запуск** | Только через `docker compose up` на локальной машине инженера. |
| **Пользователи** | Однопользовательский режим (локальная работа). |
| **Лимит оперативной памяти (RAM)** | **1–2 ГБ суммарно** на все контейнеры (жёстко ограничено через `mem_limit` в `docker-compose.yml`: потолок `1648 МБ ≈ 1.61 ГБ`). |
| **Лимит дискового пространства** | **До 15 ГБ суммарно** на все данные (сырые логи, агрегаты, индекс, отчёты). Контролируется автоматическим менеджером квот. |
| **Масштаб анализируемой системы** | От **5 до 15 микросервисов** в одном расследовании; от десятков тысяч до десятков миллионов строк логов (инцидент + несколько дней базовой линии). |
| **Основные источники данных** | 1) Файлы выгрузок из Loki, созданные внешним скриптом (`*_part-0024.json` — JSON-массивы записей `{timestamp, date, line, fields}`), а также `.jsonl`, `.gz`, `.zip`-архивы из локальной папки `./import/` или загруженные через UI.<br>2) **Прямой живой захват логов (`tilt-collector`)** из локально поднятого через **Tilt** приложения (локальный Kubernetes `kind`/`k3d`/`minikube`/`docker-desktop` и контейнеры Docker) в реальном времени! |

## 3. Основные возможности

### 3.1. Потоковая загрузка файлов и живой захват логов из локального Tilt (`tilt-collector`)
- **Живой захват из локального Tilt (`services/tilt-collector`):**
  - Автоматически обнаруживает все запущенные сервисы твоего локального окружения Tilt (по меткам `dev.tilt.resource`, `tilt.dev/resource`, `io.kubernetes.pod.name`, `io.kubernetes.container.name`, `app.kubernetes.io/name`), автоматически исключая системные контейнеры (`kube-system`, `pause` и контейнеры самого `rca-*`).
  - По нажатию кнопки **«Начать захват из Tilt»** в UI подключается к потокам `stdout`/`stderr` выбранных сервисов (с возможностью захватить хвост за последние $N$ секунд + живой поток), снимает бинарные заголовки мультиплексирования Docker и CRI-префиксы времени и отправляет батчи в `ingest-service` каждые 500 строк или 1.5 секунды.
- Чтение многомегабайтных и гигабайтных файлов `*_part-*.json`, `.jsonl`, `.gz`, `.zip` без загрузки всего файла в память (потоковый парсинг `json.Decoder` / `bufio.Scanner`).
- Защита от повторной загрузки одного и того же файла по `SHA-256` (`logs_rca.ingested_files`), исключающая удвоение счётчиков в агрегатах.
- **Автоматическое распознавание 6 внутренних схем JSON**:
  - Go `slog` + OpenTelemetry (`source: {function, file, line}`, `trace_id`, `span_id`);
  - Python / Tornado (`msg`, `level`, `line: "module:98"`, `trace` с многострочным `Traceback`);
  - HTTP access-логи Echo / Nginx (`id`, `method`, `uri`, `status`, `latency`, `error`);
  - HTTP-интерцепторы с заголовками (`http.request.headers.X-Request-Id`, `Traceparent`);
  - произвольный JSON (включая очистку грязных ключей `"license: "`, `"status:"`) и неструктурированный текст.
- **Честное определение уровня (`level`)**: исправление ошибки Loki `detected_level="error"` на успешных HTTP 200/204 логах с пустым полем `"error": ""`.
- **Контроль рассинхронизации часов (`clock_skew_ms`)**: автоматическое выявление сдвига между временем в контейнере (`time` внутри JSON) и временем записи в Loki (`timestamp`), например сдвига на +2 часа (`+7200 с`).
- **Обязательное маскирование секретов на входе**: автоматическая замена JWT (`eyJ...`), `Bearer`-токенов, `auth-token`, `Cookie` на безопасные токены `<REDACTED_JWT:hash8>` до сохранения на диск.
- **Быстрая шаблонизация (Hash-Cached Drain)**: выделение шаблонов сообщений и отпечатков стектрейсов (`stack_fingerprint`).

### 3.2. Поиск межсервисных корреляций (с `trace_id` и без него)
Поскольку сквозной `trace_id` есть только в части сервисов и логов, сервис строит **единый граф идентификаторов**:
1. Связывает `id` из access-лога с `X-Request-Id` в логе интерцептора.
2. Из того же лога интерцептора извлекает `Traceparent` и переходит к `trace_id` прикладных логов.
3. Из текста и полей прикладных логов извлекает бизнес-ключи (`visit-session-id`, `session_id`, `operator_id`, `visitor_id`, `ID`) и находит события с теми же ключами в других сервисах.
4. При отсутствии любых ID связывает события внутри одного `pod` по миллисекундной близости (`±50 мс`) и строит **межсервисный временной срез (`Cross-Service Time Slice ±2 с`)**.
5. Отфильтровывает «вечные» фоновые трейсы (например, циклы NATS-консьюмеров с десятками событий), чтобы они не склеивали несвязанные ошибки.
6. Поддерживает декларативные **профили сервисов (`./config/service_profiles.yaml`)**.

### 3.3. Автоматическое построение топологии сервисов
Сервис **без ручного описания схемы** восстанавливает граф вызовов `Service A → Service B`:
- по DNS-именам и URL внутри ошибок и логов (например, `http://chat-com.chat.svc.cluster.local:8260/l/v/init`);
- по порядку следования спанов в общих `trace_id` и бизнес-ключах (`session_id`, `visitor_id`);
- по правилам `static_upstreams` из `./config/service_profiles.yaml`.

### 3.4. Определение первопричины (Root Cause Analysis)
Для каждого кандидата `(service, template_id)` рассчитываются **8 независимых сигналов**:
1. **Цепочки запросов (S1 — Trace / ID Chains):** в каком сервисе и на какой строке кода возникает *первая* ошибка в цепочке.
2. **Время начала аномалии (S2 — Onset Detection, включая всплески латентности):** кто первым вышел за пределы нормы базовой линии по частоте ошибок или по времени ответа HTTP (`latency` $\ge 3\times$ от нормы) с точностью до секунд.
3. **Опережающая корреляция (S3 — Lead-Lag):** какой ряд ошибок стабильно опережает ряд другого сервиса.
4. **Новизна (S4 — Novelty vs Baseline + 180-дневная историческая память):** какие ошибки впервые появились в окне инцидента или выросли в $\ge 10$ раз по сравнению с базовой линией (либо с историческими агрегатами `events_agg_1m` за прошлые 180 дней), а какие являются постоянным фоновым шумом (`cache:98`).
5. **Семантика ошибки (S5 — Causal Direction):**
   - `CANCELED` (`context canceled`) — указывает **вверх** на отмену запроса клиентом/вызывающим сервисом (вызываемый сервис не виноват);
   - `DEADLINE` / `UNAVAILABLE` / `PEER_5XX` — указывают **вниз** на деградацию вызываемого сервиса;
   - `OWN_DEFECT` (`AttributeError`, `panic`, `NullPointerException`) и `RESOURCE` (`OOM`, `pool exhausted`) — указывают **внутрь самого сервиса**.
6. **Позиция в графе зависимостей (S6 — Graph Root):** поиск самого глубокого аномального узла.
7. **Точная локализация (S7 — `Where Exactly`):** конкретный `pod`, `http_route`, `service_version`, точное место в коде (`file:line`).
8. **События изменений (S8 — Change Correlation):** смена `service_version` или перезапуск `pod` перед началом сбоя.
9. **База знаний прошлых инцидентов (`RecurringCaseIDs`):** автоматическая пометка, если этот шаблон ошибки уже был первопричиной в прошлых кейсах.

На выходе формируется ранжированный список гипотез с ролями:
- 🔴 `ROOT_CAUSE` (Первопричина)
- 🟠 `PROPAGATION` (Звено распространения сбоя)
- 🟡 `SYMPTOM` (Следствие / клиентский симптом, например HTTP 500/502 на входе)
- ⚪ `NOISE` (Фоновый шум, не связанный с инцидентом)

### 3.5. Подтверждение артефактами и пакет для Gemini
- Каждая гипотеза сопровождается списком доказательств `E-01 .. E-NN` (`source_file`, `source_record_idx`, `sha256`, `redacted_line`, `logql_snippet`).
- Генерируются:
  - автономный отчёт `report.md` и `report.html` со встроенными SVG-графиками;
  - архив доказательств `evidence_<case_id>.zip` с `manifest.json`;
  - **`gemini_bundle.md`** — компактный (до 100 тыс. токенов), полностью очищенный от PII (email, имена, IP, токены заменены на детерминированные метки `<EMAIL_8f1a>`, `<USER_3c9d>`) документ с готовым системным промптом для вставки в Google Gemini.
